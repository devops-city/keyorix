### Added
- **`storage.encryption.key_dir_lock: database` for several server replicas (PostgreSQL).** With the default `flock`, every server holds an exclusive flock on `dek.lock` in the key directory for its lifetime, so a second replica on a shared ReadWriteMany keys volume refused to start wherever flock is enforced across nodes (NFSv4, CephFS, EFS), and got no protection where it is not. In `database` mode the server takes no key-directory lock: first-boot key generation and rotation crash recovery run under a PostgreSQL advisory lock (a second replica waits and loads the keys the first wrote), key-changing admin commands stay excluded by the server-presence lock, admin `--force` is refused (also when the database's record of the mode cannot be read), the live Postgres `admin backup` holds the shared presence lock, and first-boot generation is refused when the database already holds secret versions or a DEK epoch, which the first replica records before it releases the key-initialisation lock. The key directory may then be a shared volume with any flock semantics, or read-only (keys from a Kubernetes Secret). SQLite and the default mode are unchanged. Design: `docs/multi-replica-keys.md`.

### Changed
- **Schema epoch 3, compatibility floor 3: a v0.96.x binary refuses to start against a database this release has migrated** (UPGRADING.md §6q). Rolling upgrades with several replicas: see SELF_HOSTING.md, "Running more than one replica" (upgrade order, what is shared, what to avoid while old and new replicas run).

### Fixed
- **Rolling upgrade: an older replica's audit purge could drop the purged-event count for good (#3359).** A pre-#3258 binary rewrote the v2 retention anchor as v1, after which `/audit/verify` reported truncation and checkpoints answered 409. On PostgreSQL a trigger now refuses that write, so such a purge rolls back whole; the epoch floor stops older binaries from starting.
- **Rolling upgrade: an older replica's resume left the "clear synced copies" marker set, and its next plain suspend emptied the Kubernetes copies (#3362).** On PostgreSQL a trigger clears the marker on every status change away from `suspended`, whoever writes it, and the migration clears rows already left stale.
