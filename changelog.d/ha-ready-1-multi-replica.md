### Added
- **`storage.encryption.key_dir_lock: database` for several server replicas (PostgreSQL).** With the default `flock`, every server holds an exclusive flock on `dek.lock` in the key directory for its lifetime, so a second replica on a shared ReadWriteMany keys volume refused to start wherever flock is enforced across nodes (NFSv4, CephFS, EFS), and got no protection where it is not. In `database` mode the server takes no key-directory lock: first-boot key generation and rotation crash recovery run under a PostgreSQL advisory lock (a second replica waits and loads the keys the first wrote), key-changing admin commands stay excluded by the server-presence lock, admin `--force` is refused, the live Postgres `admin backup` holds the shared presence lock, and first-boot generation is refused when the database already holds secret versions. The key directory may then be a shared volume with any flock semantics, or read-only (keys from a Kubernetes Secret). SQLite and the default mode are unchanged. Design: `docs/multi-replica-keys.md`.
