### Added
- **`storage.database.single_writer` (opt-in, PostgreSQL, one server): holder lock, write fence and write epoch.** With the setting on, the server takes a per-schema advisory lock at start-up (a second server, a server without the setting, and `admin --force` are refused while it runs), installs triggers that refuse every direct database write to the security tables from any other session while it runs, and polls a write epoch with a 1 s lease. If the fence cannot be installed and verified, the server refuses to start. The live state is in the start-up log, `GET /api/v1/system/info` (`database.single_writer`) and `admin validate --posture`, with the emergency two-step for a direct change (docs/single-writer.md). The fence's fingerprint includes the trigger and function catalog rows' versions and any child table, so tampering that is undone before the next poll is still seen, and any inheritance or partitioning involving a fenced table and any change to a fenced table's columns; the fence checks every row (a write through a parent table or partition root is refused), resolves no name through the writer's `search_path` (a temp table or a function or operator of a catalog's name cannot change what it checks), and the poller compares the epoch row's version, so a write that passes the fence is seen even if the writer moves the counter back; the server's session tag is set through a bind parameter (not in `pg_stat_activity`); and `admin validate --posture` reports a deviation when the server's database role is a superuser (below-SQL changes are the one bypass the fence cannot see). This release changes no cache: reads still confirm against the database. Off by default; with it off nothing changes, except that a start-up refuses while a single-writer server holds the database and removes a fence one left behind.
