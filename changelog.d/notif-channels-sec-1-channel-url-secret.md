### Security
- **Notification channel URLs are now treated as the bearer credentials they are (#3425, #3426).** A webhook/Slack/Teams channel URL carries its token in the path. A failed delivery used to log and return the full URL (`url.URL.Redacted()` masks only userinfo), including through the wrapped transport error and the recover-admin alert broadcast; errors now name the destination by scheme and host only, and the same applies to the URL-parse error shown for a rejected channel URL. **API change (user-visible, contract v2):** `GET /api/v1/notification-channels` and `GET /api/v1/notification-channels/{id}` no longer return the channel URL to `alerts.write` callers. `url` is now scheme+host with the path elided (e.g. `https://hooks.slack.com/…`), and a new boolean `url_set` says whether one is stored. The full URL is returned exactly once, in the `POST /api/v1/notification-channels` response; the `PUT` response is the elided shape too. A `PUT` that omits `url` keeps the stored URL, and an explicit `url` replaces it. Scripts that read `url` back from list or get to reuse the credential must keep the value from the create response instead (the `keyorix notification channel` CLI prints the elided form until its next release). The web edit form no longer prefills the URL: leave it blank to keep the current one.

### Testing
- **Pinned the notification-channel SSRF guards (#3427).** `noEscalationRedirect` (a receiver answering 302 to a second host gets refused and the second host receives nothing) and the resolve-and-check loop of `validateWebhookURL` (a hostname resolving to `10.0.0.5` is refused on create and update, a resolve failure is refused) each have a test that goes red when the guard is removed.
