# DAST Rig — Technical Reference

Dynamic Application Security Testing (DAST) runs continuously against a
dedicated Keyorix instance. Findings are filed automatically as GitHub Issues.

**Source of truth**: `scripts/dast/` in this repo. The box does not pull from
git automatically — after editing a script here, copy it to
`/opt/keyorix-dast/` on CT 221 and commit the same change there too (the box
keeps its own local git history as a rebuild-survival baseline; this repo
copy is what a reviewer actually sees). `.env` and `.env.bak` are never
copied either direction — see `.env.example` here for the current variable
list (names only).

## Target stack

A dedicated Keyorix instance runs inside Docker on the LXC container, isolated
from any production environment. The `docker-compose.yml` defines two services:

| Service | Image | Role |
|---------|-------|------|
| `postgres` | `postgres:15-alpine` | Keyorix database |
| `keyorix` | Built from `server/Dockerfile` | Keyorix server under test |

The Keyorix server is configured by `/opt/keyorix-dast/keyorix-dast.yaml`:

- HTTP on port `8080`, TLS disabled (scanner talks plain HTTP inside the Docker
  network — no certificate setup needed)
- gRPC disabled (API surface is HTTP-only for DAST purposes)
- Swagger/OpenAPI endpoint enabled (`/openapi.yaml`) so ZAP can discover routes
- Rate limiting disabled (scanner would otherwise hit its own limits)
- Storage encryption enabled; KEK injected via `KEYORIX_DAST_KEK` env var
- Soft-delete retention 30 days

Secrets for the stack live in `/opt/keyorix-dast/.env` (never committed — see
`scripts/dast/.env.example` for the full current list, names only):

```
GH_TOKEN                Fine-grained PAT, keyorixhq/keyorix only, Issues:
                        Read and write + Metadata: Read, 90-day expiry --
                        used only by create-issues.sh
KEYORIX_DB_PASSWORD     PostgreSQL password  (generate: openssl rand -hex 32)
KEYORIX_DAST_KEK        32-byte hex KEK — generate once, keep forever; losing
                        it makes the postgres data volume undecryptable
KEYORIX_ADMIN_PASSWORD  Bootstrap admin password
KEYORIX_BOOTSTRAP_TOKEN First-boot bootstrap token
KEYORIX_TESTUSER_*      Persistent "viewer"-role account for scan-zap-auth.sh;
                        provisioned (not hand-filled) by provision-testuser.sh
NTFY_TOPIC              Optional; ntfy.sh topic URL lib-alert.sh pushes
                        DAST-ALERTs to. Treat the URL as a secret.
```

The admin account is created via an explicit `POST /system/init` call — NOT
automatic just because these env vars are set. Every `refresh-src.sh` run
calls it (idempotent, a no-op once already initialized) and then proves the
account actually works by logging in with it; a failure DAST-ALERTs and
aborts the run instead of silently leaving bootstrap broken.
`KEYORIX_ADMIN_PASSWORD` (and `KEYORIX_TESTUSER_PASSWORD`, generated by
`provision-testuser.sh`) must satisfy Keyorix's own password policy — a value
that's valid shell/URL-safe text but fails that policy makes `/system/init`
silently reject bootstrap. This ran silently broken for 10+ days on this box
before the assertion above existed.

## Scanner image

A single custom Docker image (`keyorix-scanner:latest`) bundles both scanners:

```
Base:    ghcr.io/zaproxy/zaproxy:stable   (provides zap-api-scan.py,
                                            zap-full-scan.py, and the ZAP daemon)
Added:   Nuclei v3.11.0 binary             (installed into /usr/local/bin/)
         Nuclei templates                   (pre-fetched at image-build time so
                                             scans run air-gapped)
```

Built with `/opt/keyorix-dast/build-scanner.sh`. Rebuild whenever:

- ZAP releases a security fix (pull new base image)
- Nuclei templates need a forced refresh (`-update-templates`)
- `NUCLEI_VERSION` in `Dockerfile.scanner` is bumped

The image is **never pulled at scan time** (`--pull never`) to keep scans
deterministic and avoid network failures mid-scan.

## Scan types and schedule

Three scans run on a fixed cron schedule (`/etc/cron.d/keyorix-dast`,
`CRON_TZ=Europe/Madrid`):

| Scanner | Script | Schedule | What it tests |
|---------|--------|----------|---------------|
| ZAP API scan | `scan-zap.sh` | Mon, Wed, Fri — 04:00 | Every endpoint declared in `/openapi.yaml` (active scan driven by the live spec) |
| ZAP full scan | `scan-zap-full.sh` | Sunday — 04:00 | Entire app surface — spider-crawls the web UI, static assets, and any routes not in the OpenAPI spec |
| Nuclei | `scan-nuclei.sh` | Daily — 06:00 | Template-based checks (auth, JWT, token exposure, SQLi, XSS, SSRF, misconfig) against all OpenAPI paths |

All three scripts use a shared **`flock` lock** (`dast.lock`) so scans never
overlap. A later-scheduled scan waits until the running one finishes before
acquiring the lock.

## Report files

| Scanner | Format | Filename pattern |
|---------|--------|-----------------|
| ZAP API scan | HTML + JSON | `results/zap-<timestamp>.html` / `.json` |
| ZAP full scan | HTML + JSON | `results/zap-full-<timestamp>.html` / `.json` |
| Nuclei | SARIF | `results/nuclei-<timestamp>.sarif` |

Nuclei emits a minimal valid fallback SARIF if it finds nothing, so
`create-issues.sh` always has a parseable file to read.

## GitHub issue creation

`create-issues.sh` runs automatically after every scan. It:

1. Parses the Nuclei SARIF (levels `warning`/`error` → Medium/High) and the ZAP
   JSON (risk codes ≥ 1, i.e. Low and above).
2. For each finding, constructs a title of the form `[DAST] <scanner>/<id>: <name>`.
3. Checks whether an open issue with that exact title already exists in
   `keyorixhq/keyorix` (using `gh issue list --search`). If one exists, skips.
4. Creates a new issue with labels `dast` and `security` if no duplicate is found.

The script is **idempotent** — re-running it after a scan that produced
duplicate findings is safe.

`GH_TOKEN` is loaded from `/opt/keyorix-dast/.env` or from the `gh`
CLI's stored credentials (`~/.config/gh/`).

Every alert `create-issues.sh` considers is first checked against
`accepted-exceptions.yaml` — see **Known accepted exceptions** below. A match
is written to `results/<sha>-accepted.txt` instead of filed, and the run
prints `N accepted exceptions suppressed`. A matched finding scoring HIGHER
risk than the entry's recorded `expected_risk` files anyway, title prefixed
`[exception risk escalated]`.

## Closing / suppressing findings

When a real fix is merged:

```bash
gh issue close <number> --comment "Fixed in PR #XXXX: <one-line explanation>."
```

For a finding that will legitimately reappear on every scan (a genuine,
permanent design tradeoff — not a scanner false positive), add an entry to
`accepted-exceptions.yaml` instead of manually re-closing it each time. See
that file's own header comment for the exact format and matching rules
(alert_ref, not bare plugin_id — ZAP rule families like 10055 have numbered
sub-checks that mean very different things; param, where it matters — the
same rule firing on a different cookie is not the same finding). Add a row
to **Known accepted exceptions** below either way, for human-readable
history.

`zap-api-scope-hook.py` (a ZAP-native `alertFilter`, loaded via
`zap-api-scan.py --hook`) has been retired — its rule-100001 suppression is
now an `accepted-exceptions.yaml` entry instead, so there's one suppression
mechanism, not two.

## Running a scan manually

SSH into the LXC container and run any script directly:

```bash
# ZAP API scan (OpenAPI-driven)
bash /opt/keyorix-dast/scan-zap.sh

# ZAP full scan (spider)
bash /opt/keyorix-dast/scan-zap-full.sh

# Nuclei
bash /opt/keyorix-dast/scan-nuclei.sh

# File issues from the most recent reports without re-scanning
bash /opt/keyorix-dast/create-issues.sh
```

All scripts are idempotent and safe to re-run. They will compete for the
`flock` lock, so a manual run will queue behind any cron scan in progress.

## Maintaining the rig

**Update the scanner image** (ZAP base or Nuclei version):

```bash
# Edit NUCLEI_VERSION in Dockerfile.scanner if needed, then:
bash /opt/keyorix-dast/build-scanner.sh
```

**Update the Keyorix binary** (after a release):

```bash
cd /opt/keyorix-dast/src
git pull origin main
docker compose build keyorix
docker compose up -d keyorix
```

**Rotate secrets** (`.env` values):

```bash
bash /opt/keyorix-dast/rotate-secrets.sh
```

Stops the stack, regenerates `KEYORIX_DB_PASSWORD`/`KEYORIX_BOOTSTRAP_TOKEN`/
`KEYORIX_DAST_KEK`/`KEYORIX_ADMIN_PASSWORD` (the admin password via
`lib-passwords.sh`'s policy-compliant generator — see below), wipes the
postgres+keys volumes (this is disposable scan-target data; confirm nothing
else references those two volumes first if that's ever not true), restarts,
re-bootstraps, re-provisions the viewer test user, and runs one authenticated
scan pass to prove it all actually works end to end. Never prints a secret
value. `KEYORIX_TESTUSER_*` and `NTFY_TOPIC` aren't touched — the former is
recreated by the volume wipe regardless, the latter isn't a rotation target.

Do not rotate `KEYORIX_DAST_KEK` without also wiping the postgres volume (this
script does both together) — the KEK is bound to the encrypted data on disk;
changing one without the other makes existing secrets permanently
undecryptable while leaving stale, now-unreadable data in place.

**Password policy**: `KEYORIX_ADMIN_PASSWORD` and `KEYORIX_TESTUSER_PASSWORD`
must satisfy Keyorix's own ADR-025 policy (`internal/core/rules/password_policy.go`
at the time this was written: 16+ chars, upper+lower+digit+special, must not
contain the account's own username/email/display-name). A value that's valid
shell/URL-safe text but fails that policy makes `/system/init` silently
reject bootstrap — this ran broken for 10+ days on this exact box before
`refresh-src.sh`'s post-bootstrap assertion existed (see above) and before
`lib-passwords.sh`'s `generate_compliant_password` replaced the old
`openssl rand -hex` generation instructions, which can never satisfy
"uppercase + special" (hex output is lowercase+digit only).

## Known accepted exceptions

Enforced by `accepted-exceptions.yaml` (see **Closing / suppressing
findings** above) — this table is the human-readable history, not the live
mechanism.

| Issue | Finding | Reason |
|-------|---------|--------|
| #1213, #1273, #1302, #1971 (closed) | `ZAP/10055` (alert_ref `10055-6`): CSP: style-src unsafe-inline | Required by the SPA's CSS-in-JS / Tailwind runtime. `script-src` does not carry `unsafe-inline`, so inline script injection (the primary XSS vector) remains blocked. Genuine (accepted) CSP gap, not a scanner false positive — expected to keep recurring on every full scan. Scoped to the specific `alert_ref` `10055-6`, not the bare `10055` family, which has other, unrelated sub-checks that must still file. |
| #1210, #1245, #1249 (closed) | `ZAP/100001: Unexpected Content-Type was returned`, for the bare target URL (`/`) and random top-level paths | zap-api-scan.py's "Unexpected Content Types" rule checks every URL ZAP visits, not just declared OpenAPI operations — including the base target URL it always hits first and assorted spider/connectivity probes. Those URLs correctly fall through to the SPA shell (`text/html`) per `server/http/router.go`'s `NotFound` handler, since they're not under any backend route prefix and must stay servable as client-side routes. Genuine API paths (`/api/`, `/auth/`, etc.) are unaffected and still enforce JSON-only content types (#1245/#1247 fixed that case in application code). |
| #1972 (closed) | `ZAP/10010: Cookie No HttpOnly Flag`, param `csrf_token` | `csrf_token` is deliberately non-HttpOnly — the SPA reads it and echoes it back as `X-CSRF-Token` for the double-submit CSRF pattern (see `server/middleware/session_cookie.go`'s `SetCSRFCookie` doc comment). Scoped to param `csrf_token` specifically — the same rule firing on `kx_session`/`kx_admin_session` would be a real bug and must still file. |
