# Install Keyorix with an AI assistant

This page lets an AI coding assistant (Claude Code, Cursor, Copilot, Codex, Aider,
a local model, ...) install and configure a fresh Keyorix server on one host,
with the secure defaults on, **without the assistant ever seeing a secret**.

How that works:

- Every secret (master passphrase, bootstrap token, first-admin password, TLS key,
  metrics token, recovery key) is generated by a `keyorix-server` command straight
  into a mode-0600 file. Commands print paths, never values.
- Commands read secrets by path (`KEYORIX_*_FILE=<path>`), never from a flag, the
  environment or the chat.
- The two steps that must show a secret to a person (MFA enrolment and, if you have
  no public key to encrypt to, the admin recovery key) are run **by you, in your own
  terminal**, not by the assistant.
- The install ends with `keyorix-server admin validate --posture`, which must print
  `No deviations found.` It also fails if the admin has no MFA, so it proves the
  whole procedure was completed.

No network access is needed beyond fetching the source. For an air-gapped host, or a
model that cannot run commands, use [`docs/install/offline-install.sh`](docs/install/offline-install.sh),
which runs the same steps as a plain script.

## The prompt

Paste this into your assistant, in a session that can run shell commands on the
host where Keyorix should run:

```text
Install Keyorix on this machine by following INSTALL-WITH-AI.md from
https://github.com/keyorixhq/keyorix exactly (fetch the raw file, or read it from
the clone you make in step 1). The install must be SECRET-BLIND. Rules:

1. Run only the commands that file lists, in order, from the install directory.
   If a command fails, stop and show me the error; do not improvise a workaround,
   do not edit anything under secrets/, keys/ or certs/, and never relax a
   security setting in keyorix.yaml.
2. Never read, print, copy, encode, hash or search the contents of any file under
   secrets/ or keys/, certs/server.key, recovery-key.age, keyorix.db, or the
   keyorix CLI credential file. No cat, less, head, tail, grep, xxd, base64, cp,
   scp, echo, printenv, env, set -x on them or on KEYORIX_* variables. Pass
   secrets only as KEYORIX_*_FILE=<path>.
3. Never ask me to paste or type a password, token, key, TOTP secret, MFA code or
   recovery code into this chat, and never put one in a command-line flag.
4. When the file says HUMAN STEP, give me the commands and wait. I run them in a
   terminal of my own, not through you (in Claude Code, not with the ! prefix),
   and I reply only "done".
5. Finish with keyorix-server admin validate --posture. Report its output, and
   list the files I must back up.
```

The rest of this page is what the assistant follows.

## Steps for the assistant

Ask the user for these first (none of them is a secret):

- **Admin email** for the first admin account (a real address with a dot in the
  domain, e.g. `admin@example.com`).
- **Recovery-key recipient** (optional): an `age1...` public key, or the path to an
  `ssh-ed25519` public key file (e.g. `~/.ssh/id_ed25519.pub`). The admin recovery key
  is encrypted to it. If the user has none, the user generates the key themselves
  in step 12.

Requirements: Linux or macOS, `git`, `make`, `curl` and Go 1.27+ (the SQLite driver is
pure Go; no C compiler is needed). The server listens on `127.0.0.1:8080` (HTTPS);
the generated config leaves gRPC off.

Run every command from the install directory `~/keyorix` (step 2 onwards). If your
shell does not keep the working directory between commands, start each one with
`cd ~/keyorix &&`. Variables set with `export` may not survive between commands
either, so each command below names the files it needs itself.

### 1. Build the binaries

Releases from v0.96.0 on have `admin generate-secrets` and `mfa enroll` (v0.95.3 and
older do not). This procedure builds from source so it always matches this document;
to use a release binary instead, take v0.96.0 or newer (see QUICK_START.md):

```bash
git clone https://github.com/keyorixhq/keyorix.git ~/keyorix-src
make -C ~/keyorix-src build
```

### 2. Create the install directory

```bash
mkdir -m 700 ~/keyorix
cd ~/keyorix
mkdir -m 700 bin
cp ~/keyorix-src/bin/keyorix ~/keyorix-src/bin/keyorix-server bin/
./bin/keyorix-server admin generate-secrets --help
```

The last command must print the help text. If it says `unknown command`, the
binary is too old: stop.

If something else already listens on port 8080
(`curl -s localhost:8080` or `ss -ltn` shows it), choose a free port now and use
it in step 4 and wherever this page says `8080`.

### 3. Generate the install secrets

```bash
./bin/keyorix-server admin generate-secrets
```

Creates `secrets/master_password`, `secrets/bootstrap_token` and
`secrets/admin_password`, mode 0600, and prints only their paths. Do not open them.

### 4. Write the config, TLS certificate and metrics token

```bash
./bin/keyorix-server admin init --config ./keyorix.yaml
```

This writes the secure-baseline config (TLS required, rate limiting, MFA required,
`/metrics` behind a token), a self-signed certificate `certs/server.crt` with its
key, and `secrets/metrics_token`, all 0600, nothing printed. Only if you chose another
port in step 2, change it now, e.g.
`sed -i.bak 's/port: "8080"/port: "18080"/' keyorix.yaml`
(`keyorix.yaml` holds no secrets; it only names files).

### 5. Generate the encryption keys and the database

```bash
KEYORIX_MASTER_PASSWORD_FILE=secrets/master_password ./bin/keyorix-server admin encryption init --config ./keyorix.yaml
KEYORIX_MASTER_PASSWORD_FILE=secrets/master_password ./bin/keyorix-server admin migrate --config ./keyorix.yaml
```

### 6. Admin recovery key (only if the user gave a recipient)

```bash
KEYORIX_MASTER_PASSWORD_FILE=secrets/master_password ./bin/keyorix-server admin recovery-key rotate --config ./keyorix.yaml --recipient RECIPIENT --output ./recovery-key.age
```

Replace `RECIPIENT` with the `age1...` key or the `.pub` path. The key is written
age-encrypted to `recovery-key.age` (0600) and never shown. Without `--recipient`
this command prints the key in plain text: **never run it that way yourself**; that
is the user's step 12.

### 7. Check the configuration before the first start

```bash
KEYORIX_MASTER_PASSWORD_FILE=secrets/master_password ./bin/keyorix-server admin validate --posture --config ./keyorix.yaml
```

Expected: `No deviations found.`

### 8. Start the server

```bash
touch server.log && chmod 600 server.log
KEYORIX_CONFIG_PATH=./keyorix.yaml KEYORIX_MASTER_PASSWORD_FILE=secrets/master_password KEYORIX_BOOTSTRAP_TOKEN_FILE=secrets/bootstrap_token nohup ./bin/keyorix-server > server.log 2>&1 &
echo $! > server.pid
curl -fs --retry 30 --retry-connrefused --retry-delay 1 --cacert certs/server.crt https://localhost:8080/health
```

The health check prints a small JSON document with `"status":"healthy"`. `server.log` contains no secrets
(the bootstrap token is pinned, so the server does not generate and log one); you
may read it if the server does not come up.

### 9. Trust the certificate in the CLI

```bash
./bin/keyorix config set ca_file "$PWD/certs/server.crt"
```

### 10. Create the first admin and the default workspace

```bash
KEYORIX_ADMIN_PASSWORD_FILE=secrets/admin_password KEYORIX_BOOTSTRAP_TOKEN_FILE=secrets/bootstrap_token ./bin/keyorix system init --server https://localhost:8080 --admin-username admin --admin-email ADMIN_EMAIL
```

Replace `ADMIN_EMAIL` with the user's address. Expected: `Keyorix initialised
successfully`.

### 11. HUMAN STEP: sign in and enrol MFA

Show the user this block and wait for "done". Do not run it yourself: it prints
the TOTP secret and the recovery codes, and asks for the password.

> Run these in a terminal of your own on this host (not through the assistant),
> from `~/keyorix`:
>
> ```bash
> cd ~/keyorix
> ./bin/keyorix login --server https://localhost:8080 --username admin < secrets/admin_password
> ./bin/keyorix mfa enroll
> ./bin/keyorix mfa activate
> ```
>
> - `mfa enroll` prints an `otpauth://` URI and a base32 secret: add it to your
>   authenticator app.
> - `mfa activate` asks for a code from the app, then the account password. The
>   password is in `secrets/admin_password`: move it into your password manager
>   first (open the file yourself), then type or paste it at the prompt.
> - Save the recovery codes `mfa activate` prints, offline.
> - Then delete the password file: `shred -u secrets/admin_password` (Linux) or
>   `rm -P secrets/admin_password` (macOS).
>
> Reply "done".

### 12. Stop the server and drop the bootstrap token

The bootstrap token is used once; remove it so it cannot be replayed.

```bash
xargs kill < server.pid
sleep 2
rm -f secrets/bootstrap_token
```

If the user gave no recovery-key recipient in step 6, this is a second **HUMAN
STEP**: ask the user to run, in their own terminal, while the server is stopped,

> ```bash
> cd ~/keyorix
> KEYORIX_MASTER_PASSWORD_FILE=secrets/master_password ./bin/keyorix-server admin recovery-key rotate --config ./keyorix.yaml
> ```
>
> and to store the printed key offline, away from this host. Reply "done".

### 13. Proof: the posture check

```bash
KEYORIX_MASTER_PASSWORD_FILE=secrets/master_password ./bin/keyorix-server admin validate --posture --config ./keyorix.yaml
```

Expected: `No deviations found.` An `admin-mfa` deviation means step 11 was not
completed; go back to it (start the server as in step 14 first).

### 14. Start the server again

```bash
KEYORIX_CONFIG_PATH=./keyorix.yaml KEYORIX_MASTER_PASSWORD_FILE=secrets/master_password nohup ./bin/keyorix-server >> server.log 2>&1 &
echo $! > server.pid
curl -fs --retry 30 --retry-connrefused --retry-delay 1 --cacert certs/server.crt https://localhost:8080/health
```

### 15. Report to the user

Show the step 13 output, then tell the user:

- **Back up together, offline:** `keys/`, `keyorix.db` and `keyorix.yaml`. Back up
  `secrets/master_password` **separately** (a password manager or a sealed
  envelope): without it every stored secret is lost, and there is no recovery.
  Keep `recovery-key.age` (or the key from step 12) away from this host too.
- `certs/server.crt` is self-signed for `localhost` and this host's name; replace it
  (same paths) with a CA-issued certificate before other machines connect.
- The server was started with `nohup`. To run it as a service, see
  [docs/SELF_HOSTING.md](docs/SELF_HOSTING.md); the service needs
  `KEYORIX_CONFIG_PATH` and `KEYORIX_MASTER_PASSWORD_FILE` (or systemd's
  `LoadCredential=`, see [ADR-099](docs/adr-099-master-passphrase-sourcing.md)),
  with the install directory as its working directory.
- Next steps: [QUICK_START.md](QUICK_START.md#use-it) (store a secret) and
  [docs/CONFIGURATION.md](docs/CONFIGURATION.md).

## What the assistant sees

Paths, file modes, the config, the public certificate, health output, command
status lines and the posture report. Never a secret value: the guardrails above
plus the commands' own behaviour (they print paths, and the two value-printing
steps are the user's) keep values out of the transcript. To check after an install,
search the assistant's transcript for a few characters of each file under
`secrets/` and `keys/`, in your own terminal.

## Troubleshooting

- `both KEYORIX_X and KEYORIX_X_FILE are set`: the shell already exports the
  plain variable; `unset KEYORIX_X` and run the step again.
- `mode 0644 is too open`: a secret file was copied or created by hand;
  `chmod 600` it.
- `generate-secrets` says `kept`: the files exist from an earlier run and are
  reused (never overwritten). To start completely fresh, the user deletes
  `~/keyorix` themselves.
- Port in use: see step 2.
